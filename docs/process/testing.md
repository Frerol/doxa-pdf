# Testing standard

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 and RFC 8174. If you depart from a SHOULD, say so in the PR and why.

This standard applies to every test in this repository, whether a person or an agent wrote it. [AGENTS.md](../../AGENTS.md) has the short form.
The test levels (unit, engine, widget, golden, device) and the Definition of Done are in [06 — Quality Assurance](../plan/06-quality-assurance.md).

## 1. What a test is for

A test states an **invariant**: something that must stay true however the code changes. It fails when a plausible change breaks that invariant.

Before you add a test, you SHOULD be able to write three lines about it:

1. **Invariant:** what it guards, in one sentence.
2. **Breaking change:** a plausible change that breaks it. Plausible means something a person could do while fixing, refactoring or extending this code: an off-by-one, a reordered step, a dropped case, a changed default, a swapped coordinate system. Deleting the function does not count.
3. **Only this test:** no other test fails on that change. Check by searching the tests for the function.

If you cannot write all three, the test SHOULD NOT be added. Regression tests for **saving files** and for **safety** (hostile input, data loss) are the exception: when in doubt, keep them.

## 2. What not to test

A test SHOULD NOT check:

- code a reviewer can verify by reading: a getter, a one-line mapping, a `copyWith`;
- constants, default values or exact numbers we chose, unless other code depends on that exact value (a file format field, a PDF key);
- wiring: that widget A contains widget B, or that a call is forwarded unchanged;
- the behaviour of Flutter, Dart, PDFium or a dependency, rather than our use of it;
- generated code (`*.g.dart`, `app/lib/l10n/gen/`).

## 3. How to write assertions

- Tests SHOULD assert **behaviour seen from outside**: what the user or the caller gets, not private state.
- Tests SHOULD assert **relations** where the exact value is our choice: "inside the page", "wider than before", "changed", "in reading order", "before the next frame". Use exact values when the value is a fact: PDF coordinates from a fixture, the text of a page, a decoded field.
- Tests MUST NOT depend on wall-clock time or real delays. Use fake time (`tester.pump(duration)`, injected clocks). When a test checks timing, compare it with the named constant or the budget it must beat (`kDoubleTapTimeout`, a 220 ms turn), not with a bare number.
- Floating-point geometry SHOULD use a tolerance (`closeTo`, `moreOrLessEquals`).
- Tests SHOULD reference requirement IDs in the test or group name when they verify one (`FR-VIEW-017`, `NFR-PERF-004`).

## 4. Bug fixes

- A bug fix MUST add a test that fails without the fix, unless the fixed code is a few lines a reviewer can check by reading. Say which in the PR.
- Before opening the PR, run the new test once with the fix reverted and confirm that it fails.
- A crash or hang on bad input SHOULD add that input to the package's hostile-input tests (for example `doxa_dict`'s malformed files, or the engine's broken PDFs).

## 5. Never weaken a test to pass a check

- You MUST NOT delete, weaken, skip (`skip:`) or loosen a test to make a check pass. A failing test is a finding: fix the code, or show in the PR why the test is wrong.
- Removing tests that fail the rules above SHOULD happen in a PR of its own, which MUST list every removed test and the reason.
- A flaky test SHOULD be fixed, not retried. If it cannot be fixed at once, open an issue and mark the test `skip:` with the issue link, in its own PR. A test that fails every time is not flaky and MUST NOT be skipped.

## 6. Where tests go

| Code | Tests | Notes |
|---|---|---|
| `packages/doxa_core`, `doxa_dict`, `doxa_ink` | `test/` in the package, `dart test` | Pure Dart, enforced by `dependency_rule_test.dart` |
| `packages/doxa_engine`, `pdfium_ffi` | `test/` in the package, `dart test` | Need PDFium (`tools/fetch_pdfium.sh linux`) |
| `app/` | `app/test/`, `flutter test` | Widget tests use `FakePdfEngine` and the helpers next to the tests |
| `packages/doxa_platform` | Dart tests and Kotlin unit tests | Android behaviour is checked on the device |

`tools/check.sh` runs all of them and MUST pass before a PR.

## 7. Fixtures

- Test PDFs live in `test_corpus/`, with source and licence for each file in `test_corpus/MANIFEST`, following the [clean-room standard](clean-room.md#5-fixtures-and-test-corpus).
- Small fixtures SHOULD be generated by a committed script (`tools/generate_corpus.py`, or a generator next to the package's tests), so they can be rebuilt and reviewed.
- Large files are fetched by `tools/fetch_corpus.sh` into the git-ignored `test_corpus/external/`, pinned by SHA-256. Tests that need them SHOULD skip with a clear message when they are missing, and CI SHOULD fetch them where it runs those tests.

## 8. Checks that cannot run in CI

Stylus feel, latency, frame timing and visual results need the reference tablet ([AGENTS.md §4](../../AGENTS.md#4-environment-maintainers-machine)).

- Performance MUST be measured on a **profile** build on the device, never in unit tests or debug builds.
- The PR MUST say which device checks ran, with what result (for example the `DOXA-PERF` numbers), and which are still pending. A check that did not run MUST NOT be reported as passed.
