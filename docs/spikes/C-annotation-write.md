# Spike C — Writing annotations and interoperability

- **Issue:** #7 · **Date:** 2026-11-24 · **Result: GO, with a changed save strategy** (see [ADR-0008](../adr/0008-annotation-save-strategy.md))
- **Engine:** PDFium 160.0.8179.0 (chromium/8179) through `pdfium_ffi`
- **Prototypes:** `spikes/annot_write/` (desktop) and `spikes/saf_lab/` (Android) on the
  [`spike/annot-write`](https://github.com/Frerol/doxa-pdf/tree/spike/annot-write/spikes) branch (not merged)
- **Renderers checked:** PDFium (≈ Chrome), pdf.js 6.5 (Firefox), MuPDF 1.28, Poppler 26.11 (Okular/Evince), all automated;
  a **commercial Android PDF reader** on the reference tablet (manual). Acrobat is not installed on the tablet and remains to be checked.

## Test material
Generated PDFs with four text lines: a plain page, `/Rotate 90`, `/Rotate 270`, a CropBox with a non-zero origin, and a page with a
"foreign" Text annotation carrying an unknown key (`/Foo`). Also a 155 MB / 300-page image-heavy file (scanned-book stand-in),
the same files re-saved by qpdf with a classic xref table and with **xref streams**, a file annotated in that **commercial reader**, and one of the maintainer's own PDFs with 31 existing annotations.

## Findings

### 1. How each annotation type gets a good appearance (`/AP`)
| Approach | Result |
|---|---|
| **E1** Highlight with AP from `FPDFAnnot_SetAP(string)` | ❌ PDFium writes the stream **without `/Resources`**, so there is no ExtGState and **no Multiply**. The yellow covers the text in PDFium, pdf.js and MuPDF. |
| **E2** Highlight / Underline / Squiggly with AP **generated by PDFium** | ✅ Correct (`/BM /Multiply` for highlights). Generation only happens when the page is **rendered with `FPDF_ANNOT`**, see §3. |
| **E2'** Markup saved **without AP** | ✅ pdf.js, MuPDF, Poppler, PDFium **and the commercial reader** all draw them correctly, and the commercial reader can select and edit them. |
| **E3** Ink with AP from **page objects** (`FPDFAnnot_AppendObject`) | ✅ Variable-width filled outline. Highlighter ink keeps `/BM /Multiply`. Identical in all renderers and in the commercial reader. |

Rules discovered for `FPDFAnnot_AppendObject`:
- **`FPDFAnnot_SetBorder` deletes an existing AP**, and `FPDFAnnot_SetColor` **fails** once an AP exists. Set every dictionary value first and **append the appearance objects last**.
- In that order, the object-based AP survives rendering, saving and reopening.

### 2. Geometry
- Quad points from `FPDFText_GetRect` (user space, Acrobat order UL-UR-LL-LR) land on the right words in every renderer.
- On `/Rotate 90/270` pages, annotations rotate with the page consistently everywhere.
- With a CropBox, annotations stay in user space. Those outside the crop are clipped consistently. (`pdftoppm` renders the MediaBox by default, which is a tool default and not a defect.)
- **Still to verify in `doxa_engine`:** the screen → user-space transform (rotation + CropBox offset) for *user-drawn* ink, with unit tests.

### 3. PDFium's incremental save is not usable
| Problem | Evidence |
|---|---|
| It rewrites **every object loaded in the session**, not only modified ones | After visiting 30 pages of the 155 MB file, each save appended **+15.5 MB** (images rewritten). Autosave would grow the file without bound. |
| **Malformed output for xref-stream PDFs** | The appended xref stream lacks `/Type /XRef` and `endobj`. qpdf reports "file is damaged" (MuPDF tolerates it). |
| Rendering with annotations **modifies foreign annotations** | PDFium generated an AP for the AP-less foreign Text note, added `/PDFIUM_HasGeneratedAP true` and **changed its `/Rect`**, and the incremental save wrote it out. |

### 4. PDFium's full save works
| Check | Result |
|---|---|
| Valid output (classic xref, xref streams, all variants) | ✅ `qpdf --check` clean |
| Foreign annotations untouched (when the page was not rendered with `FPDF_ANNOT`) | ✅ byte-identical dictionaries and AP data |
| Annotations made in the **commercial reader** survive a Doxa edit + save | ✅ all visible annotations identical, including its vendor-specific private keys and AP streams. One orphaned object that the other app itself had replaced was dropped. That is correct garbage collection, not data loss. |
| Speed, 155 MB file, desktop | 90–135 ms (in memory) |
| Speed, 155 MB file, **Galaxy Tab S10 FE**, streamed to a temp file | **272 ms** |

### 5. Android Storage Access Framework (risk R6)
Picker (`ACTION_OPEN_DOCUMENT`) → persistable read+write permission → copy in → PDFium full save to a temp file → write back with
`openOutputStream(uri, "wt")` → read back and compare SHA-256.

| File | Read | PDFium save | Write back | Verified |
|---|---|---|---|---|
| 1 KB | 29 ms | 2 ms | 8 ms | ✅ |
| 155 MB | 169 ms | 272 ms | 208 ms | ✅ |
| Maintainer's PDF with 31 annotations | 81 ms | 44 ms | 9 ms | ✅ (32 annotations, shown in the commercial reader) |

The whole cycle for 155 MB is **< 1 s** (NFR-PERF-008: ≤ 2 s). All three files came from `com.android.externalstorage.documents`.
**Not yet verified:** a cloud provider (Google Drive's own `DocumentsProvider`), where `"wt"` truncation and write support vary. The read-back check in the
prototype is the safety net, and a provider without `FLAG_SUPPORTS_WRITE` must fall back to "Save a copy" (FR-FILE-010).

### 6. What other apps write (commercial Android reader)
It uses UUIDs in `/NM`, always writes an AP for its own annotations, stores **per-point pen pressure in a vendor-specific array key** parallel to `/InkList`,
and saves incrementally. It also adds an AP to AP-less foreign annotations. Generating an AP for someone else's annotation is common practice, but Doxa should still avoid it.

## Decisions (see [ADR-0008](../adr/0008-annotation-save-strategy.md))
1. **Save = PDFium full save, streamed to a temp file, verified, then atomically replaced** (`rename` on desktop; SAF `"wt"` + read-back verification on Android). **Never use `FPDF_INCREMENTAL`.**
2. **Text markup (highlight, underline, squiggly) is written without `/AP` in the MVP.** Every tested reader generates it correctly, and Doxa draws its own markup in Flutter anyway.
3. **Ink gets an object-based AP** (filled variable-width outline; Multiply for the highlighter), appended **after** all dictionary values. `/InkList` holds the centreline and `/DoxaPressure` the raw pressure.
4. **The editing document instance is never rendered with `FPDF_ANNOT`.** Foreign annotations are rendered from a separate, read-only instance (input for ADR-0005, Spike A).
5. Read known vendor-specific per-point pressure arrays when present, so pen strokes from other apps keep their variable width when shown or edited in Doxa.
6. **Post-MVP:** an own **incremental-update writer** in Dart (`doxa_engine`) for true append-only saves with full AP control. It brings back FR-SAVE-004 and makes signed PDFs safe to annotate.
