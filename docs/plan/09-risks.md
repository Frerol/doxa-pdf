# 09 — Risks

Likelihood (L) and impact (I) use the scale Low/Med/High. Review this register at the end of every milestone. **Last review:** end of M0 (2026-11-25), after Spikes A–D.

| ID | Risk | L | I | Mitigation | Owner/When |
|---|---|---|---|---|---|
| R1 | **Ink latency** in Flutter misses the budget on Android (no front-buffer rendering in Flutter) | Low | High | **Retired by Spike B:** 5–7 ms event → raster on the reference device ([ADR-0006](../adr/0006-ink-rendering-in-flutter.md)). Remaining checks before v0.2: camera test, and frame times against the 90 Hz budget (11.1 ms) with the production reader (Spike D measured against 60 Hz) | M0 ✓, M2 |
| R2 | **Stylus support gaps on desktop** (affects M5/M6, not the Android MVP): Flutter Windows/Linux embedders may not expose pen pressure/tilt/eraser reliably | High | High | Not covered by Spike B (Android only): a desktop stylus spike on real hardware opens M5. Fallbacks: contribute upstream fixes, or a small platform plugin that reads Windows Pointer/WM_POINTER and GTK tablet events | M5 |
| R3 | **PDFium crashes** on hostile files take down the whole app (in-process native code) | Med | Med | Fuzzing, timely PDFium updates, journaling so no annotations are lost. Evaluate out-of-process engine (Android service / desktop subprocess). Not addressed in M0: the production engine (M1) must survive a failed open, and fuzzing starts with the corpus | M1 → M4 |
| R4 | **Annotation interop bugs** (rotation, CropBox, appearance streams) make notes look wrong in other readers | Low | High | Spike C: identical in PDFium, pdf.js, MuPDF, Poppler and a commercial Android reader, incl. rotated/cropped pages. Keep automated cross-renderer tests; Acrobat still to check before v0.2 ships | M0 ✓, M2 |
| R5 | **F-Droid** requires building PDFium from source; the build is heavy and fragile | High | Med | Reproducible PDFium build script; ask F-Droid maintainers early; GitHub Releases/Obtainium cover the MVP meanwhile | M5–M7 |
| R6 | **Android storage (SAF)** makes atomic in-place saves hard (content URIs, cloud providers) | Med | High | Spike C: temp → `"wt"` → SHA-256 read-back works on local storage (155 MB in < 1 s). Stays Med until cloud providers are verified; no `FLAG_SUPPORTS_WRITE` → "Save a copy"; journal guarantees recovery | M2 |
| R7 | **Foreign annotation layer** approach (draw own types in Flutter, others in PDFium) proves complex | Low | Med | **Resolved by Spike A:** read-only render instance with Doxa annotations hidden in memory ([ADR-0005](../adr/0005-rendering-pipeline-and-foreign-annotations.md)) | M0 ✓ (closed) |
| R8 | **Scope creep** toward a general PDF editor before the study core is excellent | Med | Med | Tier model in Vision §5; every new area needs an ADR; milestone exit criteria | Ongoing |
| R9 | **Bus factor of one** (single maintainer) | High | High | Excellent docs, good-first-issues, CI that enforces quality, clear governance | Ongoing |
| R10 | **Trademark / look-alike concerns** with commercial apps that inspired the feature set | Med | Med | Layout and workflows deliberately follow familiar commercial-reader conventions ([UX §8](05-ux-design.md#8-familiar-layout-and-workflows)), so the visual identity stays original: own name, logo, icons, colours and texts; no copied assets; no other product is named in the repo, store listings or marketing | Ongoing |
| R11 | **Code signing costs** (Windows SmartScreen, Play account fee) | Med | Low | SignPath OSS program; budget for the Play developer fee; MSIX via winget | M6–M7 |
| R15 | **Full saves break digital signatures**, and AP-less markup depends on readers generating appearances (PDF 2.0 requires an AP) | Med | Med | Detect signed PDFs and warn / offer "Save a copy"; own incremental writer with real APs post-MVP ([ADR-0008](../adr/0008-annotation-save-strategy.md)) | M2, post-MVP |
| R12 | Flutter platform breaking changes / pinned version drift | Low | Med | FVM pin, upgrade once per milestone in a dedicated PR | Ongoing |
| R13 | **OCR on-device** is slow or memory-hungry on large scanned books, or its text layer misaligns with the image (bad highlights) | Low | High | **Mostly retired by Spike D:** ≤ 2.6 s per dense page, ≈ 40 MB extra RSS, word boxes aligned, smooth reading and ink during OCR, cancel ≤ 0.2 s ([ADR-0007](../adr/0007-ocr-integration.md)). Open in M4: a wide-Unicode font for the invisible text, rotated/cropped pages, detecting existing OCR layers, recognition quality | M0 ✓, M4 |
| R14 | **Large textbooks** (1000+ pages, 100 MB+) exhaust memory or make search/thumbnails slow | Med | High | Spike A: first page ≤ 151 ms, no janky frames on 1000-page and 155 MB files; RSS peaked at 385 MB on the scanned book, and OCR adds ≈ 40 MB (Spike D). The production reader stayed stable across open/close cycles on the reference tablet (NFR-PERF-006). Test a 4 GB device | M0 ✓, M1 |
| R16 | **Dictionary files in the wild** vary (encodings, broken or huge indexes, HTML definitions) and the feature grows alpha 1 | Med | Low | StarDict only, validated on import; definitions rendered as a safe text subset; small generated fixtures and malformed-file tests ([ADR-0009](../adr/0009-offline-dictionary.md)) | M1 |
| R17 | **Later network features** (cloud, OPDS, KoSync) bring proprietary services, OAuth client IDs and store/F-Droid anti-feature labels, and the KOReader ecosystem is AGPL | Med | Med | REST APIs only, never proprietary SDKs; consider a separate build flavour for proprietary clouds; implement KoSync from the protocol, never copy AGPL code; ADR per area | later |
| R18 | **EPUB** needs a reflow engine and an annotation storage model that differ from PDF | Med | Med | ADR before work: evaluate GPL-compatible engines (no MuPDF) and a storage format for highlights/comments | later |
| R19 | **PDFium cannot write the outline or page labels** (bookmark and page-label APIs are read-only), needed by FR-BOOK-003 and FR-UTIL-002 in the MVP | High | Med | Spike before M3: write `/Outlines` and `/PageLabels` through a GPL-compatible library (for example qpdf, Apache-2.0) or a small object writer after the full save; record the choice in an ADR | M2–M3 |
| R20 | **OCR supply chain:** Tesseract4Android 4.9.0 comes as a prebuilt AAR from JitPack, and F-Droid needs a source build | Med | Med | Pin version and checksum; before the first release with OCR, build the AAR from the tagged source in CI or vendor a verified artefact ([Spike D](../spikes/D-ocr.md#limits-and-follow-ups)) | M4, M7 |
